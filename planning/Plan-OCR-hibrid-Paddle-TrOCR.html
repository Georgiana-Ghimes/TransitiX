1. Problema și obiectivul

Sidecar-ul OCR actual folosește PaddleOCR cu latin_PP-OCRv3_mobile_rec, antrenat pe text tipărit. Pe scris de mână, confidența cade des la 0,1–0,3 și textul e greu de folosit în facturare.

Obiectiv

  • Tipărit: Paddle + fallback când câmpurile esențiale lipsesc / conf slabă.
  • Scris de mână: TrOCR-small ONNX pe CPU + fallback controlat.
  • Acuratețe maximă pe demo, consum minim RAM/VRAM.

Hardware demo (self-hosted)

  • 4 GB RAM (strâns) · GTX 1060 Ti · Ryzen 7 4800H
  • Inferență CPU în container (GPU nefolosit în v1)
  • Profil MEMORY_PROFILE=tight: 1 request, DET_SIDE 1280, TrOCR lazy+unload, clasificator heuristic

2. Constrângeri

  • Node.js neschimbat — același POST /ocr / /ocr/json pe port 8100.
  • Preprocess existent păstrat (perspectivă, auto-rotate, DET_SIDE_LEN=1920, DROP_SCORE=0.10).
  • Fără Qwen / modele >1B / PaddleOCR-VL / llama.cpp.
  • Câmpurile de business rămân în Node; sidecar adaugă metadate (needs_review, linii, stats).
Optimizare pe 4 GB: un OCR o dată; DET_SIDE=1280; fără MobileNet în RAM (heuristică); TrOCR lazy + unload după request; ORT 1–2 thread-uri; pass-uri foto limitate; RSS în /health. Dacă baseline (doar Paddle) deja OOM pe VM → nu adăuga TrOCR pe aceeași cutie fără swap sau mutare sidecar. Implementarea nu pornește până comanda explicită „începe”.

3. Soluția propusă

  1. PaddleOCR detectează zonele de text.
  2. Clasificator ușor (MobileNetV3 ONNX / heuristică CPU): printed vs handwritten.
  3. Printed → Paddle; handwritten → TrOCR-small ONNX.
  4. Fallback-uri pe praguri de confidență / lungime.
  5. Validare câmpuri desemnate + needs_review.
  6. Măsurători: zone Paddle vs TrOCR, timp, documente în review.
TrOCR-small ONNX: consum minim, potrivit pentru demo. Export cu greedy decoding (fără beam search) — acceptabil pe demo. Vocabular BPE obligatoriu la export; pin-uiește tokenizers în requirements.txt la aceeași versiune ca la export (mismatch = text stricat / crash).

Gate 1 — probe ambele căi Paddle 2.9

probe_det_rec.py rulează întotdeauna ambele: (A) ocr(det/rec flags) și (B) text_detector + text_recognizer. Chiar dacă A „pare OK”, B se testează — pe 2.9 A poate fi inconsistentă. Pipeline-ul folosește doar calea stabilă. Dacă ambele căi sunt flaky: STOP — investighează versiunea PaddleOCR / modelul latin_PP-OCRv3_mobile_rec; nu forța pipeline-ul pe fundație instabilă.

5. Pipeline tehnic

  1. Preprocess existent → detecție (API din Gate 1).
  2. Clasificare printed / handwritten per crop.
  3. Printed → Paddle; dacă conf < 0,5 → TrOCR.
  4. Handwritten → TrOCR la 384×384 (resize + padding, fără stretch). Crop-uri foarte late (aspect > 10:1, ex. 2000×50): padding centrat umple prea mult cu alb — preferabil tăiere în bucăți sau padding diferit (notă în trocr_onnx.py). Conf < 0,75 sau lungime < 2 → paddle_fallback.
  5. Agregare + field_check + răspuns extins (Node citește în continuare text).
paddle_fallback: text slab, dar prezent cu încredere scăzută — nu se exclude din validare (altfel needs_review pe aproape tot).
Ruta / adresa lungă (HW): nu blochează demo-ul. (1) Split TrOCR pe crop-uri late (aspect >10:1); (2) OPTIONAL_FIELDS=ruta,adresa — warning, nu missing_fields; (3) lexicon fuzzy pe localități/străzi (lexicon/ro_places.txt). Ținta client: TPO, dată, nr. auto, TRO, cantitate. Adresa poate rămâne „de confirmat”.

Observabilitate

  • GET /health: contoare + hybrid: true|false din HYBRID_OCR.
  • POST /debug/classify: crop → stil + confidență.
  • ONNX versionat: trocr-small-handwritten-v1.onnx + vocab + sha256.

8. Ce nu facem

  • Nu scriem cod hybrid înainte de raportul baseline.
  • Nu oprim probe-ul la prima cale care „pare OK”; dacă ambele flaky → STOP, nu forțăm pipeline.
  • Nu exportăm TrOCR ONNX fără vocab BPE / fără pin tokenizers aliniat.
  • Nu judecăm hybrid-ul dacă HYBRID_OCR=0 deja diferă de baseline.
  • Nu schimbăm setul de avize între baseline și hybrid.
  • Nu stretch-uim TrOCR; strip-uri >10:1 → split / pad special.
  • Nu excludem paddle_fallback din field_check (verificare manuală 2–3 docs).
  • Nu modificăm Node.js / portul sidecar-ului.
  • Nu introducem modele VL grele pe GPU pentru acest demo.
Mesaj pentru asociați: extensie a sidecar-ului OCR existent, nu rescriere a aplicației. Succesul se măsoară pe același set de documente reale — baseline vs hybrid — inclusiv confidențe.
