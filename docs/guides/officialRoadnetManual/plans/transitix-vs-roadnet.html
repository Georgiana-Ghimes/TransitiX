Analiză competitivă & plan de implementare

Ruta Transitix

Ce vinde Roadnet Transportation Suite, ce are Transitix azi, și drumul concret — schemă, servicii, ecrane — până la un TMS care le trece înainte pe terenul lor și le rămâne inaccesibil pe al nostru.

Bază de cod: Transitix v1.9.0 Branch: RAI-spedition Orizont: 6 faze / ~5–7 luni Data: 25 aug. 2026
Punctul de plecare

Ce se poate lua de fapt dintr-un TMS

Roadnet nu are cod de furat — e un stack Win32 de 30 de ani, închis. Ce se poate lua e modelul de date și setul de constrângeri, iar acelea sunt publice: descrise în broșura lor și vizibile în capturile de ecran. Planul de mai jos reconstruiește acel model din specificație, cu componente open-source pentru părțile grele (motor de rutare, solver VRP), și adaugă stratul pe care Roadnet nu-l va avea niciodată în România: ANAF, e-Transport, CMR, tahograf.

Concluzia scurtă a analizei: Transitix nu are azi conceptul de „oprire”. O cursă e un document CMR punct-la-punct — un expeditor, un destinatar, o dată de încărcare. Roadnet trăiește într-un model comandă → oprire → rută → scenariu. Fără acel model, nimic din Routing, Territory Planner sau FleetLoader nu are unde să se agațe. Faza 1 este, de aceea, cotitura arhitecturală a întregului plan.

Unde se câștigă de fapt

Paritatea pe rutare te aduce la egalitate; nu îți câștigă o licitație. Diferențiatorul e ultima treime a tabelului: e-Transport, e-Factura, CMR digital, 561/2006 modelat nativ în optimizator. Roadnet e un produs american care în România se vinde prin integrator; conformitatea ANAF nu e și nu va fi în roadmap-ul lor. Un optimizator care planifică pauza de 45 de minute și repausul zilnic în rută, nu ca raport ulterior, e ceva ce Roadnet Routing nu face.

Cotitura

Modelul nou: comandă → oprire → rută

trips rămâne exact ce e — documentul de transport CMR, potrivit pentru FTL cap-coadă, care e majoritatea traficului intern românesc. Peste el se așază un strat de distribuție, strict aditiv, care nu strică nimic din ce merge azi. O rută poate genera unul sau mai multe CMR-uri; o cursă existentă rămâne validă fără rută.

-- locatii geocodate, master data partajata (clienti, depozite, puncte de lucru)
CREATE TABLE locations (
  id UUID PK, company_id UUID NOT NULL, client_id UUID NULL,
  name, address, city, county, postcode, country DEFAULT 'RO',
  lat NUMERIC(10,7), lon NUMERIC(10,7),
  geocode_source TEXT, geocode_confidence NUMERIC(3,2), geocode_verified BOOL,
  default_service_time_min INT DEFAULT 15,
  window_start TIME, window_end TIME,
  max_vehicle_length_m NUMERIC, access_notes TEXT,
  territory_id UUID NULL
);

-- comanda: unitatea care trebuie mutata
CREATE TABLE orders (
  id, company_id, client_id, location_id,
  order_number TEXT, type TEXT,        -- livrare | ridicare | schimb
  requested_date DATE, window_start TIME, window_end TIME,
  service_time_min INT, weight_kg, volume_mc, pallets INT,
  requires TEXT[],                     -- ADR, frigo, lift-hidraulic, ...
  status TEXT, route_stop_id UUID NULL
);

-- ruta: o zi de lucru pentru un vehicul + sofer
CREATE TABLE routes (
  id, company_id, route_date DATE, code TEXT,
  vehicle_id, driver_id, depot_location_id, scenario_id NULL,
  planned_distance_km, planned_duration_min, planned_cost,
  actual_distance_km, actual_duration_min, actual_cost,
  status TEXT   -- draft | planificata | lansata | in_executie | finalizata
);

CREATE TABLE route_stops (
  id, company_id, route_id, seq INT,
  location_id, order_id NULL,
  kind TEXT,    -- depot_start | livrare | ridicare | pauza | repaus | depot_end
  planned_arrival TIMESTAMPTZ, planned_departure TIMESTAMPTZ,
  actual_arrival TIMESTAMPTZ,  actual_departure TIMESTAMPTZ,
  leg_distance_km, leg_duration_min, status TEXT,
  UNIQUE (route_id, seq)
);

CREATE TABLE route_scenarios      (id, company_id, route_date, name, params JSONB, kpis JSONB, is_committed BOOL);
CREATE TABLE route_exceptions     (id, company_id, route_id, route_stop_id, type, severity, detected_at, acknowledged_at, acknowledged_by, payload JSONB);
CREATE TABLE territories          (id, company_id, name, color, polygon JSONB /* GeoJSON */, metrics JSONB);
CREATE TABLE telematics_positions (id, company_id, vehicle_id, route_id, lat, lon, speed, heading, ignition, recorded_at, source);
CREATE TABLE load_plans           (id, company_id, route_id, strategy, metrics JSONB);
CREATE TABLE load_items           (id, load_plan_id, order_id, sku, x, y, z, l, w, h, bay, axle_group, load_seq);

Regulă neîncălcabilă (deja în AGENTS.md): fiecare tabelă nouă primește company_id NOT NULL REFERENCES companies(id) ON DELETE CASCADE plus index compus pornind de la company_id, și fiecare intră în ENTITY_MAP din server/src/entities.js cu lista ei de câmpuri scriibile. gps_logs nu se șterge — devine proiecția „ultima poziție cunoscută” peste telematics_positions, ca să nu se rupă pagina GPS existentă.

Execuție

Planul, în șase faze

Fiecare fază livrează ceva utilizabil în producție. Estimările sunt săptămâni-om pentru un dezvoltator familiar cu baza de cod; P0–P2 sunt strict secvențiale, P3 și P4 pot merge în paralel.

P0

Fundația geospațială

2–3 săpt.

Nimic din restul planului nu funcționează fără coordonate și distanțe reale. Faza asta nu adaugă ecrane noi — face ca cele existente să spună adevărul.

Livrabile

  • Tabela locations + backfill din clients.address și din adresele de expeditor/destinatar deja existente în trips.
  • Serviciu de geocodare server/src/lib/geo/geocode.js — Photon self-host, scor de încredere, cache pe adresă normalizată.
  • Ecran de verificare a geocodării: locațiile sub prag, cu pin mutabil pe hartă și marcaj geocode_verified.
  • Sidecar OSRM în docker-compose.yml + server/src/lib/geo/osrm.js cu route(), table() (matrice), nearest().
  • Cache de matrice în Postgres, cheie pe perechea de noduri snapped, cu TTL — altfel P2 recalculează inutil aceleași distanțe în fiecare zi.
  • trips.distance_km se calculează automat la salvare, cu suprascriere manuală păstrată.
Criteriu de acceptare

Peste 95% din clienții activi au coordonate cu încredere ≥ 0,8. POST /api/geo/matrix cu 100 de locații răspunde sub 2 secunde. Distanța unei curse București–Cluj cade la ±3% față de Google Maps.

P1

Comenzi, rute, opriri — și board-ul de dispecerat

3–4 săpt.

Cotitura arhitecturală. După faza asta, planificarea se face manual dar corect; optimizatorul din P2 devine un buton peste un model care deja funcționează.

Livrabile

  • Schema orders, routes, route_stops + intrările corespunzătoare în ENTITY_MAP.
  • Import comenzi din XLSX/CSV — exceljs e deja în server/package.json; se refolosește tiparul de mapare a coloanelor din modulul de avize.
  • Ecran nou /dispatch: coloană stângă cu comenzi neplanificate, coloană dreaptă cu rutele zilei, hartă în centru. Drag-and-drop comandă → rută, reordonare opriri, recalcul instant al km și ETA prin OSRM.
  • Generare CMR: o rută produce automat câte un trip per destinatar, cu numerotare din contorul existent.
  • Foaie de parcurs printabilă per rută (PDF prin jspdf, deja instalat).
  • Aplicația de șofer afișează ruta ca listă ordonată de opriri, nu ca o singură cursă.
Criteriu de acceptare

Un dispecer planifică manual 40 de comenzi pe 5 vehicule în sub 15 minute, tipărește foile de parcurs, iar șoferii văd opririle în ordine în aplicație.

P2

Optimizatorul — paritate cu Roadnet Routing, plus 561/2006

4–5 săpt.

Aici moare stub-ul din src/pages/PlanningAI.jsx și pagina devine ce pretinde că e. optimization_suggestions supraviețuiește, dar alimentată din diferența dintre planul curent și cel optimizat — adică sugestii cu cifre reale în spate.

Livrabile

  • Sidecar VROOM + server/src/lib/planning/solver.js care traduce comenzi și vehicule în job-uri și vehicule VROOM.
  • Constrângeri: ferestre de timp pe oprire, capacitate pe trei dimensiuni (kg, mc, paleți), skill-uri (ADR, frigo, lift), depozite multiple, tura șoferului.
  • Post-procesor Reg. 561/2006: inserează pauza de 45 min după 4h30 de condus și repausul zilnic ca opriri reale în route_stops, apoi re-verifică ferestrele. Asta e capabilitatea care trece înaintea Roadnet, nu doar la egalitate.
  • Scenarii: același set de comenzi rulat cu parametri diferiți (cost/km, penalizare depășire fereastră, număr maxim de vehicule), salvat în route_scenarios, comparat pe KPI într-un tabel, cu promovarea unuia singur în plan.
  • Rulare mărginită în timp (30–60 s), cu sămânță din planul zilei precedente pentru convergență rapidă.
Criteriu de acceptare

200 de comenzi pe 15 vehicule, optimizate sub 30 de secunde. Comparație A/B între două scenarii, cu diferența pe km, ore, cost și număr de vehicule. Zero încălcări de timp de conducere în planul generat.

P3

Execuție live — paritate cu Roadnet Dispatcher

3–4 săpt.

Se elimină simularea GPS. Planul din P2 capătă un contra-plan: realizatul.

Livrabile

  • telematics_positions + ingest: aplicația de șofer trimite poziții (Geolocation API, buffer offline), plus POST /api/telematics/ingest cu cheie per companie și adaptoare pentru Webfleet, Frotcom, Teltonika.
  • Motor de excepții: întârziere la oprire, sosire prea devreme, abatere de traseu, oprire neplanificată, staționare prelungită, viteză excesivă. Fiecare scrie în route_exceptions cu severitate și cere confirmare de la dispecer.
  • Recalcul ETA în cascadă: o întârziere la oprirea 4 împinge automat 5…12 și declanșează notificare către clienții afectați (se refolosesc client_confirmations și lib/email.js).
  • Board live prin SSE: hartă cu vehicule, culoare după starea de excepție, bară plan vs. realizat per rută.
  • Reluare istorică: traseul realizat suprapus peste cel planificat, pentru o zi aleasă.
  • ePOD complet în aplicația de șofer: semnătură, poze, motiv de refuz — legat de route_stops.
Criteriu de acceptare

O rută reală urmărită de la lansare la finalizare, cu ETA-uri care se ajustează la fiecare poziție primită și cu excepțiile ridicate în sub 60 de secunde de la producere.

P4

Plan de încărcare și teritorii

4–5 săpt.

FleetLoader și Territory Planner. Se pot construi în paralel cu P3 — nu depind de telematică.

Livrabile — încărcare

  • warehouse_products se extinde cu lungime/lățime/înălțime, greutate unitară, stivuibil da/nu, clasă ADR, tip palet.
  • Packer 3D extreme-point în server/src/lib/loading/packer.js, cu două strategii: driver-friendly (LIFO — ultima oprire se încarcă prima) și warehouse-friendly (grupat pe SKU și zonă de picking).
  • Calcul sarcină pe axe cu avertisment la depășire — chestiune de amendă în control rutier, nu doar de optimizare.
  • Ecran de vizualizare a încărcăturii: profil lateral al remorcii cu procent de umplere per compartiment, în linia capturii FleetLoader, dar în browser.

Livrabile — teritorii

  • Clustering capacitat peste locațiile geocodate, ponderat pe volum, număr de opriri și timp de condus.
  • Poligoane GeoJSON prin Turf.js, editabile manual pe hartă.
  • Tabel de echilibru: opriri, kg, mc, ore estimate per teritoriu, cu abaterea față de medie.
  • Atribuire automată locations.territory_id → filtrare implicită în planificarea zilnică.
Criteriu de acceptare

Umplere ≥ 85% pe un set real de comenzi, cu ordinea de încărcare respectând secvența inversă a opririlor. Cinci teritorii generate automat, cu abatere de sarcină sub 15%.

P5

Dashboards și șanțul românesc

3–4 săpt.

Faza care transformă paritatea în avantaj comercial. Nimic de aici nu există în Roadnet și nimic nu va exista.

Livrabile — dashboards

  • Model de cost per vehicul: motorină, salariu șofer, taxe de drum, amortizare, întreținere — din care rezultă cost real per km, per oprire, per kg livrat.
  • Vederi materializate pentru KPI, reîmprospătate nocturn: punctualitate, km goi, grad de umplere (greutate și volum), plan vs. realizat pe km și ore, cost per comandă.
  • Cockpit peste recharts, cu detaliere până la rută și oprire. Export XLSX prin tiparul report_templates deja existent.

Livrabile — conformitate RO

  • e-Transport: obținere automată a codului UIT la lansarea rutei, cu popularea trips.uit_code, reîncercări și stare de sincronizare vizibilă.
  • e-Factura: SPV real, XML UBL, semnătură, urmărirea statusului — înlocuiește simularea din invoices.efactura_status.
  • Tahograf: import fișiere .ddd de card și de vehicul, raport de infracțiuni, alertă la apropierea limitelor săptămânale — cuplat înapoi în optimizatorul din P2, care astfel știe cât mai poate conduce fiecare șofer mâine.
Criteriu de acceptare

O factură emisă și acceptată în SPV fără intervenție manuală. Un cod UIT obținut automat la lansarea unei rute. Optimizatorul refuză să aloce un șofer care ar depăși limita săptămânală de conducere.

Ce poate merge prost

Riscuri și cum se dezamorsează

Calitatea geocodării pe adrese rurale

Cel mai probabil punct de eșec al întregului plan. „Sat Cornu, com. Brebu, jud. Prahova” nu se rezolvă curat în OSM. Dezamorsare: scor de încredere obligatoriu, ecran de corecție prin pin, cache permanent per companie — o adresă corectată o dată rămâne corectă. Bugetează două săptămâni de curățare de date la prima implementare reală.

Optimizatorul dă rezultate pe care dispecerul le refuză

Un plan matematic optim care contrazice cunoașterea locală se abandonează în prima săptămână. Dezamorsare: planul optimizat intră ca propunere, nu ca decizie; dispecerul mută orice oprire, iar sistemul recalculează și îi arată costul modificării. Cu timpul, refuzurile repetate devin constrângeri explicite în model.

Erodarea a ceea ce funcționează deja

Modulul de avize și fluxul CMR sunt partea matură a produsului. Straturile noi sunt strict aditive: trips nu-și schimbă schema în P1, gps_logs rămâne ca proiecție în P3. Fiecare fază păstrează suita Vitest verde înainte de merge.

Costul de infrastructură

OSRM, Valhalla, Photon și VROOM înseamnă patru containere în plus și un extract OSM al Europei — undeva la 8–16 GB RAM pe un VPS. E de aproximativ zece ori mai ieftin decât licențierea unui motor comercial de rutare, dar nu e gratis, și trebuie prins în modelul de preț per client de la început.

Izolarea multi-tenant sub presiune

Zece tabele noi înseamnă zece ocazii de a uita company_id într-un WHERE. Dezamorsare: un test care enumeră toate tabelele company-scoped și verifică prezența coloanei și a indexului, plus revizuire dedicată pe fiecare interogare nouă din server/src/routes/.

De unde se începe

Primii trei pași

  1. Ridică OSRM local. Un container, extractul OSM al României, și un test care cere distanța București–Cluj. Dacă răspunde în sub 100 ms, întreaga fază P0 e validată tehnic într-o după-amiază.
  2. Adaugă locations și geocodează clienții existenți. Rezultatul îți spune imediat cât de mare e problema de curățare a datelor — și, implicit, dacă estimarea de 2–3 săptămâni pentru P0 ține.
  3. Scoate DemoBanner de pe pagina GPS abia la finalul lui P3. Până atunci, onestitatea etichetei „demo” valorează mai mult decât aparența unei funcționalități care nu există — e și motivul pentru care baza de cod actuală e ușor de extins.
