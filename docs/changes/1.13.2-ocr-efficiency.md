# 1.13.2 — OCR fără CPU irosit

Versiune: web/API 1.13.2 · companion 1.9.2 (build 66)

## Ce consuma resurse degeaba

| Problemă | Efect |
| --- | --- |
| Endpoint-urile `async` din sidecar rulau OCR sincron | `/health` înghețat cât procesa → Node vedea `paddle-down` → upload-uri marcate Eșuat |
| fail-stale la 90s vs buget OCR 300s | rânduri aflate în coadă picate, OCR rulat oricum, rezultat aruncat |
| VL cu timeout propriu după clasic | o poză slabă ținea CPU-ul 2× timeout |
| VL pe CPU (bench) | 266s / 0 caractere; 4 din 5 fișiere timeout la 300s; clasic 0,7–6,6s |
| Fetch abandonat de Node | sidecar-ul continua minute întregi pe un răspuns necitit |
| Fără limită globală | batch-uri diferite trimiteau joburi în paralel pe același CPU |
| EXIF ignorat | poze de telefon ajungeau culcate → 3 rotații în plus |
| Pagini 2+ fără cod TPO | 4 rotații pe fiecare pagină |

## Ce s-a schimbat

- Node: coadă globală (`OCR_CONCURRENCY`, implicit 1), un deadline comun pentru coadă + clasic + VL, `budget_ms` trimis sidecar-ului.
- Node: VL doar dacă textul clasic e slab, PDF ≤ `OCR_VL_MAX_PAGES` (2), buget rămas ≥ `OCR_VL_MIN_BUDGET_MS` (90s); circuit breaker după `OCR_VL_MAX_MISSES` (2) → pauză `OCR_VL_COOLDOWN_MS` (30 min).
- Node: rândurile în lucru sunt excluse din fail-stale și din marcarea „OCR down”; status reverificat înainte de OCR.
- Sidecar clasic: OCR în threadpool sub lock, oprire la deadline (504), refuz dacă bugetul s-a consumat în coadă (503), EXIF, warmup la pornire, `busy`/`waiting` în `/health`.
- Sidecar VL: lock, deadline între pagini, `max_pages` din request, EXIF; `PADDLE_OCR_VL_PDF_PAGES` implicit 2.

## Pe VM

1. Scoate / comentează `PADDLE_OCR_VL_URL` din `server/.env` și oprește containerul VL dacă rulează (`docker compose -f docker-compose.paddle-ocr-vl.yml down`).
2. Rebuild sidecar clasic: `docker compose -f docker-compose.paddle-ocr.yml up -d --build`.
3. Repornește API-ul.

Sidecar-ul vechi e compatibil (ignoră `budget_ms`), dar fără rebuild `/health` rămâne blocat cât procesează.
